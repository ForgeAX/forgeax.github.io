ForgeAX agora é open source: um motor de jogos feito por IA, para IA

O ForgeAX (Tiangong em chinês) agora é open source: um motor de jogos desenvolvido quase inteiramente por agentes de IA e projetado desde o primeiro dia para ser usado por IA.

npx -y @forgeax/marker@0.5.0 install

Source: github.com/ForgeAX/forgeax-engine · Apache-2.0

01 Great engines, built for humans

For two decades, every design decision in a game engine has served a human sitting at a screen. Visual editors let you drag and drop scenes. Blueprints and simplified scripting lower the bar for building logic. Assets are authored in DCC tools, imported, then packed into binaries for compact storage. All of those choices were right for their time, because the user was a person.

Now put an AI in that seat. It can't read binary assets. It can only operate editor buttons through screenshots and computer use. It can't fit a million lines of C++ into one conversation. So today the common way for AI to drive a commercial engine is through a bridge like MCP: the engine exposes a few wrapped APIs, and the AI presses them.

That's handing the AI a TV remote. It can change channels and turn up the volume, but when a wire comes loose inside the set, it can't see it and can't fix it.

This approach has two problems. First, the AI can't see what's happening inside the engine, so when the picture is wrong it can only guess. Second, every vendor's bridge is different and keeps changing, so models never see a stable way to use them during training. The results are unreliable.

And real games are complicated. Almost no engine covers everything a serious game needs out of the box, so studios and solo developers end up forking a version and modifying it heavily.

So here is our bet: engine companies have years of head start, but when it comes to being used by AI, everyone is back at the same starting line.

02 The next engine's first user is AI

AI keeps getting better at writing code. At this pace, it could soon rewrite any given program from scratch.

Follow that logic and you reach a slightly counterintuitive conclusion: a pre-built, tightly sealed engine that the AI can't change may be an obstacle rather than a help. Routing around it and rewriting it is often faster.

If you can't stop that, hand over the tools. Don't give the AI a remote. Give it a screwdriver.

The first page of the ForgeAX engineering guidelines says: AI is the first user. When what works for AI conflicts with human habit, AI wins.

In code, that turns into a set of concrete choices.

The language AI knows best. Engine, scripts, assets and game logic are all TypeScript, running on WebGPU. The type checker catches the AI's mistakes immediately, and everything above the WebGPU layer is something the AI can read, modify and rewrite.

The UI AI knows best. There's no custom UI framework. Game UI is standard HTML and CSS. Even inside WeChat mini-games, which have no browser, the engine renders that same HTML and CSS itself.

Never hidden, even if not wrapped. We ask the team for robust code, but the rule is that the AI may choose not to change something; it must never be unable to see it. We also follow a principle we call "compression is intelligence". What gets compressed is concepts, not files: game state lives in one place, render data lives in one place, and everything else reads without copying. Every time the AI doesn't have to ask "which copy is the real one?", that's one less bug.

We used to pick technology by maturity. Now we pick whatever works best for AI.

That's how we built ForgeAX, an AI-native engine.

Why ForgeAX

  1. A different kind of tool. No editor-shaped container. ForgeAX is driven by agents and lives entirely in the npm ecosystem that today's coding harnesses already use. It boots fast inside a sandbox and supports hot reload.
  2. A different way to make assets. Procedural assets are supported from the ground up, a workflow AI can actually reason about, and AI's modeling and procedural skills keep improving. Traditional assets such as FBX are supported too.
  3. AI built into the runtime. ForgeAX ships runtime AI interfaces. The NPC module can bind a character to an AI "soul" for agent-driven NPCs. AI can output parameters for procedural map generation at runtime, or rebalance numbers, items and mechanics on the fly. That opens room for AI-native gameplay.
  4. Fits your workflow and platform. Whatever coding harness or foundation model you use, opening a ForgeAX project gives it the same usage guide. The two games below were made with different harnesses and different models. One project builds to a web page, a single HTML file or a WeChat mini-game with one command, and it can be packaged as a desktop or mobile app.
  5. Recursive self-improvement, together. ForgeAX grows alongside foundation models, harnesses and the community.

Here's what that looks like on two real games.

03 Make a game with Codex: two commands and one brief

No editor, no code written by hand, only Codex. What can it ship? Here is the whole path. You can follow it as written.

Step 1. Add ForgeAX to Codex. You need Node.js 22.13 or newer.

npx -y @forgeax/marker@0.5.0 install --ide codex

Without --ide, it sets up every supported AI coding tool on your machine at once (Claude Code, Codex, Cursor and others). The command writes the ForgeAX tool entry, MCP plus a command line, into your Codex user configuration. Unlike a bridge with a few buttons, everything behind that entry is open to Codex: the engine source, the runtime state and a GPU capture of every frame.

Step 2. Create a project in an empty directory.

mkdir spirit-stones && cd spirit-stones
npx -y @forgeax/marker@0.5.0 init

The directory has to be genuinely empty. init creates an empty game project in it: nothing in the scene yet, but it already passes the project check and builds.

A note on versions: the commands above are the ones on the website today. The entry package is @forgeax/marker, and a new project gets engine 0.5.0. We re-ran both commands in a fresh user directory; they succeed, and the empty project passes its check and build. The session shown below was recorded on November 23, when the entry package was still named @forgeax/game (engine 0.4.8), so that is the name you see at the start of the video. The two commands are used the same way.

Step 3. Open Codex in that directory and say what you want, once. A good brief covers four things: what the player does, what changes on screen, what counts as done, and what has to be verified. This is the brief we sent on November 23, word for word:

This is an empty project created with ForgeAX. Turn it into an original small 3D game called Spirit Stone Night: the scene is a moonlit night (deep blue sky, cool moonlight, low ground mist); 12 glowing spirit stones are scattered around the level, slowly rotating and floating; when the player walks close, collect the stone automatically with a small burst of light particles; show "Spirit Stones n / 12" in the top-left HUD and "Moonlit Harmony" when all are collected. Read AGENTS.md first and follow the project conventions.

One limit on this machine: a browser cannot be opened here and browser pages may not be left running, so do not start forgeax dev or any browser, and do not publish or upload anything. Your shell has no network access. Verify with forgeax project check, forgeax project build and automated tests of the game logic instead, and say plainly what is still unverified in a real browser. I will open the build myself and send you a screenshot if something looks wrong. Work only inside this project folder. The sandbox here does not allow writing .git, so I will make the commit; when you're done, tell me how to play.

The first paragraph is the game. The second is the rules of our machine, not of the engine. We ran Codex in a sandbox: no network from its shell, no browser, no write access to .git. So in this run three things were ours: opening the build in a browser, playing it on a keyboard, and making the git commit. If your machine has no such limits, you can swap the second paragraph for "when you're done, run it with forgeax dev, take screenshots to check the visuals yourself, and commit with git", and let Codex look for itself. We did not test that variant in this run. One more detail: this was an unattended, non-interactive run. In that mode Codex's own approval policy blocks calls to the ForgeAX MCP tools, which is what happened in an earlier run of ours. This time it only read resources through the MCP entry and did the work through the forgeax command line and the guides that ship with the engine.

It took two turns and 16 minutes 39 seconds of Codex time. Nobody wrote a line of code by hand.

Turn 1: the brief (13 min 4 s). Codex read AGENTS.md, the project's AI-facing guide, then the usage guides that ship with the engine. The empty project has no camera and no character, so it chose what to put there: a traveller carrying a lantern, a moonlit island and twelve named stones. It built all of it in code: the island with its pines and distant ridges, the stones, a burst of light for each pickup, a "field journal" panel with the counter, and a small island chart that marks the stones still out there. It used no external assets, and its shell had no network anyway. The rules for walking and collecting are kept apart from rendering, so they can be tested without a browser. It wrote 7 tests, among them one that runs the game from the first stone to the twelfth and then restarts it. It hit three problems on the way, fixed each one, and wrote them down in the project's feedback file. It finished with the project check, the production build and every test green. It also said plainly what it could not verify: start-up in a real browser, how the keys feel, and the final look of the moonlight, mist, particles and HUD.

We opened the build. It did not start. The page said "Unable to start the game." and printed the engine's own diagnostics: the journal panel had failed during start-up, with parseGuid is not a function. A green project check, a green build and 7 green tests had not caught it.

Turn 2: we paste the diagnostics back (3 min 35 s). Codex traced the failure to its own code. The journal panel asked for its layout through a service that, on the interface side of the game, can only read published assets; the call it used exists only on the full asset registry. It found this by reading the engine code installed in the project, without patching the engine or switching versions. It first wrote a test that reproduced the exact error, then changed the one call, and the test passed.

The second build starts and plays clean: 12 of 12 stones on a real keyboard, "Moonlit Harmony", R to restart, no errors in the browser. The result is 8 source files, 572 lines of TypeScript, plus the panel's layout and one particle shader, and 8 automated tests.

It doesn't always take two turns. The same day we ran the same brief in Chinese. That run was a single session of 10 minutes 6 seconds. It produced 8 tests, and the build started and played through in the browser on the first try. The Chinese edition of this article shows that run.

We ran this brief more than once that day. An earlier pair of runs used the previous model: three turns in English (22 min 55 s) and one in Chinese (11 min 47 s). The same paragraph made a different game every time.

Green tests are not a correct picture. The problem in this run passed every offline check and only showed up in a browser. This time we were Codex's eyes. The diagnosis and the fix were its own, and what made them possible was diagnostics the engine prints by itself and engine code the AI can read. That's the difference between a remote and a screwdriver: when something breaks, the AI can open the machine and look. With a browser available it can go further and take a frame apart with the frame capture tool, which these runs did not use:

This path isn't specific to Codex. Claude Code, Cursor and other general coding agents open the same project and read the same AGENTS.md and the same commands.

04 Five days, one transforming mech game

Spirit Stone Night is the baseline. To probe the ceiling, we ran a long-horizon test: Tiangong Warframe, a two-form mech shooter. In the air you fly the "Falcon" in a vertical bullet-hell; on the ground it transforms into the third-person "Frame". You launch from a hangar, fight through air and ground battles up to the stratosphere, and face one of three final bosses depending on your rating.

Mech, environments, enemies, effects, UI, sound effects and music are all generated in code, with zero external assets, and the whole game was made by one person. Content development took 5 days and 274 messages (18,321 Chinese characters). From those, the AI made 2,401 commits and left about 3,400 process screenshots. The mech in that five-day build has 25 joints and transforms between fighter and mech. 103 sound effects, 58 boss-attack sounds and 9 adaptive music tracks are all synthesized live.

The first prompt wasn't "make a mech game". It was a ~4,000-character spec covering scope, technical constraints and acceptance criteria. A few of the rules: use only ForgeAX, no external assets; one clear takes about 5 minutes, with a new set piece every 20 to 30 seconds; a sub-agent that didn't work on the game reviews screenshots blind, and a pass needs an average of 4.0 or higher; if the AI thinks a bar is unreasonable, it can only file it under "pending ruling", never lower it on its own. With a high bar, every round leaves another round of work, so the AI stays on course through hours nobody is watching.

On day two, the creator noticed the AI was recording their requests in less and less detail: a sentence with five points would shrink to half a line in the notes. So we added a requirements ledger. Every message gets an ID, is broken into checkable requirements, and every status needs evidence. In the first version, only 67 of 167 items were actually done; most were partial. The most important rule: anything visual can't be marked as passed by whoever built it; it has to be compared against the reference image. The sea of clouds is the example. The AI glanced at a screenshot and marked it passed. The next day the creator looked: solid spheres with sandpaper grain, like steamed buns. All of it was thrown out and rebuilt.

There was no mech modeler in the engine, so the AI first wrote itself a set of modeling tools, then used them to build the mech. The creator's notes on the head were brief: it must not look like a fly, especially the mouth guard; match the reference proportions with a long head; straight V-shaped horns. Every round, the AI put the head side by side with the concept art. The head went through 12 rounds and 123 images; the body went through 26 more rounds for head-to-body proportion. In round 18 the AI replaced the big slanted eyes with a thin visor slit and changed the crest to a short, wide blade. (Recent engine releases build these modeling capabilities in.)

After the five-day build, the mech itself moved on a generation. The one in the hangar and head screenshots above is the body from the five-day build. It was assembled piece by piece with tools the AI wrote on the spot, mostly by extruding simple solids; its chest and shoulder armour is folded from flat plates. Since then the engine has grown modeling tools of its own: meshes generated from curves and surfaces, UV unwrapping, baking high-poly detail onto a low-poly mesh. We had the AI rebuild the hero mech from scratch with them. The new body is called YINTAI, and it is the one in the recording at the top of this section: continuous curved armour all over, 30 joints, one mesh shared by the mech and the fighter, 72,157 triangles in the in-game model. It is still just code: 8 source files, about 4,100 lines of TypeScript, with no imported models or textures.

How it was built, surface by surface, is written up in YINTAI: a game mech modelled entirely in code, and the 3D model can be turned around in the browser. The point for this article is narrower: the gaps a game exposes turn into engine capabilities, and once those land, the AI can rebuild what it made before with the new ones.

The AI checks its own work. The game can jump straight to any shot on command, and the AI then plays with real keyboard and mouse input, from the menu all the way to the boss results screen. That gives it an edit, screenshot, look, edit-again loop, and the creator only has to look at pictures.

Why insist on code for everything? Because the AI can't really modify models and textures imported from outside. When everything is code, the AI can change anything and verify the change immediately. That said, ForgeAX also imports FBX, GLB and glTF with PBR materials and skeletal animation. The AI is free to choose: call external modeling tools, bring in existing assets, or use models from third-party generation APIs.

05 Everything grows, persists, and gets reused

Two trends define the harness era.

Everything is a plugin. Rendering is a plugin. Physics is a plugin. Your game is a plugin too: package it and another project can install it whole; uninstall it and it leaves with its own undo button, nothing left behind.

Assets are code. An asset can be written in TypeScript and batch-generated in a loop, or it can be a JSON file where one changed field shows up as a readable diff. Every asset has a stable ID, so references survive moving between projects. The harness manages assets the way it manages its own memory files.

People often ask: if AI is this capable, why not have it write an engine from scratch every time? It would be fast. The problem is reuse. If you write one and I write one, your assets mean nothing to my project. Both trends point to one goal: what you've built should be remembered. A module from game A runs in game B. The assets and mechanics from your first game carry into your second. When the next generation of models arrives, AI can rebuild them with new capabilities. Call it an engine with memory, a GitHub for games, or a world whose content, mechanics and framework evolve themselves.

06 A self-evolving engine

ForgeAX's first commit was on May 2, 2026. By October 19, the repository had 3,611 commits, 74 packages and 4,034 test files, with nearly 600 commits in the previous 30 days.

Most of that code wasn't written by people. The engine is evolving itself, and it's speeding up.

Here's the division of labor: humans set direction and accept work; large numbers of cloud AI agents write code, run tests and review each other in sandboxes, and approved changes are merged by an owner. There are seven steps: requirements, research, planning, implementation, verification, acceptance and merge. Humans own steps one and six, and every step has to leave evidence a machine can check. The agent fleet developing the engine runs on a scaled-out pool of Mac minis and Windows machines with gaming GPUs, a real-hardware environment where it iterates on performance and on the game-making experience in parallel.

Every engine change has to pass acceptance. Each round uses a fresh batch of game tasks that were never used to tune the engine, so it can't have been "fit to the answers". The same AI builds the same task several times with ForgeAX and with a baseline, and judges who don't know which image came from which side score the visuals alone.

Plans, rationales and failed attempts all go into the repository. When a stronger model arrives, it can read the history and see why a piece of code was written the way it was. If it was a compromise forced by an earlier model's limits, the new model can change it confidently and knows where to go.

You can watch that pace in the public repository. Stable v0.5.0 shipped on November 12, two weeks after the previous stable release, with several directional lights, temporal anti-aliasing and far wider WebGL2 rendering. Stable v0.5.1 followed one week later and made water, volumetric clouds, desktop and mobile app packaging and a CPU, memory and GPU profiling workbench stable. Between the two, preview builds came as fast as four in two days. Community requests are part of it: on November 5 a developer asked in a GitHub issue for spot lights to control falloff the way point lights do, and two weeks later SpotLight.decay shipped in stable v0.5.1. Every update is written up in the changelog.

One step further: as AI moves toward self-improvement, the game industry will change with it. The more AI uses this engine, the more help it gets finding and fixing its own problems.

07 Honestly, it's still early

ForgeAX is at the beginning, with a lot of room to grow. For now it best serves indie games that ship across platforms, and individuals or teams who want AI deeply involved in development.

There are three main limitations today.

Mobile performance. In WeChat mini-games and similar environments, frame rates aren't yet a stable 60 fps. That needs deeper optimization.

Platforms and ecosystem. Native console and mobile targets, content tooling and commercial track record still trail mature engines. We're actively working on them.

The cost of making games with it. On the same fresh tasks, AI still spends more than we'd like completing them with ForgeAX, because foundation models haven't been trained on our engine. Even so, the AI-native design means models that have never seen the engine can still build with it. We're working with model teams, and we'll open-source more high-quality ForgeAX games for the community and model builders to learn from. As models get stronger, the engine evolves faster, and making games with a model, a harness and ForgeAX gets freer and smoother.

We're not claiming you can make a AAA game from one sentence. AI lets you turn ideas into games more freely, but good games still come from a creator's ideas, taste, judgment and long hours of polish.

Closing

Future virtual worlds may be maintained entirely by AI. Gameplay code, narrative and media assets will be AI-generated, at a complexity far beyond what people can read. Players and game experts will still supply the intent and the final taste.

That's why it matters to give AI an engine it can fully control: a mature scaffold, so it doesn't start from zero every time.

This is our gift to AI: an engine built natively for AI, a seed for a virtual-world oasis.

It only gives the world a place to grow. It's the first gradient. The rest is up to AI and creative human makers.

Get the full source on GitHub, and add ForgeAX to the AI coding tool you already use with one command:

github.com/ForgeAX/forgeax-engine

npx -y @forgeax/marker@0.5.0 install

We'd love for AI and pioneering game creators everywhere to build with ForgeAX and turn ideas into games. Contributions are welcome too: code, write-ups of what you've built, and feedback. Let's build the AI-native game engine for a new era together.
